
## Running the Liana extension

- Run `npm install` in this folder. This installs all necessary npm modules in both the client and server folder
- Open VS Code on this folder.
- Press Ctrl+Shift+B to start compiling the client and server in [watch mode](https://code.visualstudio.com/docs/editor/tasks#:~:text=The%20first%20entry%20executes,the%20HelloWorld.js%20file.).
- Switch to the Run and Debug View in the Sidebar (Ctrl+Shift+D).
- Select `Launch Client` from the drop down (if it is not already).
- Press ▷ to run the launch config (F5).

## Building the local authoring backend

The extension uses the local `pareto_liana` and `liana_authoring` packages.
`npm run compile` compiles both packages before the client and server, so the
VSIX contains the current schema implementation:

```sh
npm run compile
node --test test/*.test.mjs
npm run bundle
```

The backend and bundled authoring template use the promoted, namespace-aware
Liana contract exclusively. `Type Specification` contains `schema` and a recursive
`directory` file tree. Each file node declares its `file extension` and selects
an entry in `schema.structure.types`.
The schema has separate `structure` and `resolver` trees:

- Structure nodes contain `namespaces`, `basic types`, and `types`.
  Every structural type has explicit `public`, `private`, or `private single use`
  visibility. File roots, cross-namespace component targets, and their component
  resolver declaration benchmarks must be public. Both private states allow
  local/local-cyclic components and cross-namespace type, signature, and result
  references. Reuse counts are not enforced.
- `resolver` contains separate `declarations` and `implementations` trees.
  Declarations contain signatures with `values` and `lookups`; value references
  include a structural `subselection`. Each tree contains `namespaces` and `types`.
- Child namespaces retain their own type, signature, and resolver lookups; they
  are not flattened. Type and component locations are `local`, `child namespace`,
  and `sibling namespace`; structural components also support `local cyclic`.
  Sibling namespace dependencies remain acyclic. Component resolver declarations
  must match the structural target. Sibling locations are unavailable at root.
  Runtime implementation dispatch uses resolved declaration identity, with a
  document-wide implementation index shared through nested contexts. Sibling
  property selections retain their `sibling` tag. Old location tags are rejected.
- Basic types describe `double quoted` or `undelimited` tokens with optional
  structural regular expressions and optional `hyperlink` metadata. They no longer imply numeric, boolean, date,
  text-link, or multiline-text semantics. Patterns match the entire token value.
  Completion uses a placeholder when no valid token can be inferred.
- List and state results are optional value references. Optional values wrap
  their `value` and `constraints`. Derived references are no longer supported.
- Optional resolvers include a `presence` selection. When specified, the optional
  must be set exactly when that selection is set. Presence is checked before
  branch constraints and payload resolution; invalid or unavailable prerequisites
  do not count as absence.

The server applies the manually authored root resolver with the same name as
the structural root type. Resolver namespaces, signatures, and implementations
must cover their structural counterparts, as required by the schema contract;
the server does not synthesize semantic resolvers. Computed metadata such as `resulting type`,
`definition`, and `signature` is resolved by the reader, not serialized as `~`
placeholders in schema input.

The template is the promoted self-schema context from
`clean_start/instance/liana/.liana/schema.slna`. The bundled schema models,
ASTN readers, and serializers are generated by `liana_to_pareto` followed by
`generate_typescript_from_pareto_patched`. For the visibility upgrade they retain
the bootstrap first-layer model from
`clean_start` commit `078ced91` (`instance/liana/liana_next.liana.lna`), matching
the promoted processors' model. They are not generated from the now-inlined
second-layer self-description. The deployed template and fixture documents use
the latest inlined schema. The maintained semantic reader was
migrated from `clean_start/meta/tools/liana_to_pareto/src/schema/resolve.ts`. Keep those contracts
aligned when updating the tools and the extension. The extension's maintained
reader additionally validates dense explicit argument dictionaries.
Both client commands and the server load the template through the local
`pareto-liana` reader. The maintained resolving reader lives in
`pareto_liana/src/modules/schema.generated/schemas/resolved/refiners/unresolved_manual.ts`;
the historical split reader paths re-export that implementation.

This is a breaking schema-format update: existing authoring environments must
have their schemas migrated and their `.liana/schema.slna` contexts regenerated
before using this extension. Installing it does not promote the tools or
authoring environments in `clean_start`.

The regression suite covers namespace-isolated references, navigation, rename
and completion through both child and sibling components; invalid sibling targets,
declaration mismatches and namespace cycles; required resolver coverage; token patterns and quoting; schema
round-tripping; and existing benchmark, constraint, and result behavior.
Visibility coverage includes all three completion options, rejection of missing
or invalid visibility, both private states in local/local-cyclic components,
private cross-namespace signature and result references, public-only
cross-namespace components/resolver declarations and roots, and round-tripping
the promoted Liana, accounting, and Pareto fixtures.

For packaging without committing or bumping the version automatically, run
`vsce package --no-dependencies -o ../out/liana-<version>.vsix` after the build.
The top-level `build_package.sh` commits all open changes, so it is not appropriate
when unrelated work is present.
